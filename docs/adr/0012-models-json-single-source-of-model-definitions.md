# models.json as the single source of Model definitions, edited by tools/assets-editor

Accepted, amended by [ADR 0021](0021-game-objects-one-file-each-validated-by-generated-json-schemas.md) (zod schemas) and [ADR 0022](0022-model-ids-decoupled-from-file-paths.md) (Model ids). Gameplay data of buildings now lives in `assets/buildings.json` ([ADR 0014](0014-all-buildings-defined-in-buildings-json.md)). Models come from four sources (Kenney and Quaternius zips under `assets/{kenney,quaternius}/`, hand-made GLBs under `assets/managed-models/`, Poly Pizza GLBs under `assets/poly.pizza/`) and their sizes were scattered: `docs/asset-catalog.json` for Kenney footprints, hard-coded `limits` in `natureModelFit.ts`, rail fits in `railModelFit.ts`, notes in the viewer's `localStorage`. A Model definition (footprint, scale or fit, rotation offset, baked node scale, recolor, source, license, author, url, note) now lives in `assets/models.json`, one entry per existing game model key. Derived facts (bounding box, triangles) are never stored: they are measured on demand.

The game imports the file at build time. A model without an entry falls back to computed defaults (footprint `ceil(bbox - 0.15)`, scale 1, no recolor), so production never crashes on a missing entry; a vitest check fails on orphan entries, key collisions across sources, invalid footprints or colors, and a missing license. Existing keys are kept (renaming would break saves and code), so the source is shown beside the key rather than prefixed. `docs/asset-catalog.json` is replaced by `models.json`; `docs/asset-catalog.md` stays as the conventions document.

`tools/assets-editor/` (formerly `prototypes/asset-viewer/`) is the asset management tool: it lists the four sources, edits `models.json` through a dev-only Vite endpoint, previews recolor with the same shader as `ModelLibrary`, and adds assets (GLB drop, Poly Pizza import, Kenney or Quaternius zip) and removes hand-made or Poly Pizza models not used in the game. The file operations live in testable modules under `scripts/`; the Vite plugin is a thin HTTP adapter. A license is required to add an asset. The editor never commits, and wiring a new asset into gameplay (buildings, roles, tiers) stays manual code.

Rejected: prefixing keys with the source (breaks saves), a schema library (a shared TS type and a test are enough), a separate server for the editor (a Vite plugin suffices), renaming and editing zips or GLBs from the tool.
